# Annotation toolbar at the canvas minimum

The annotation toolbar now uses the existing `StudioControlRow` native horizontal scroll container. It retains the original HStack, dividers, Spacer, centered alignment, controls, bindings, actions, stroke range/width-slider size, enabled states and menu commands. Removing the tool picker's 280-point cap lets its native segmented control retain its intrinsic width. There is one instance of each control across resizing; overflowing controls remain in the scroll document.

The unchanged 9cb68c9 toolbar, compiled with the same final fixture, fails its first 320-point layout proposal: it reports 689 × 208 points at an 11-point font in Select mode. A discarded wrapping prototype passed outer bounds but a stronger native intrinsic-size check found that its picker compressed a 364-point native control into 268 points at the largest tested font. Those exploratory results are retained as failed/incomplete evidence, not qualification of the final implementation.

`python3 apple/scripts/test_annotation_toolbar_layout.py --report /tmp/annotation-layout.json --artifacts apple/build/annotation-toolbar-layout` compiles the complete shipping toolbar and `StudioControlRow`, the actual annotation value models and text-style definitions, and extracted actual annotation UI state and hex-color code. Only external owners are inert memory stand-ins; production dispatcher, store and workspace constructors never run. All actions are inert and no action is invoked. The fixture mounts hidden non-key borderless windows with activation prohibited and never orders them onscreen. It uses no capture, images, global input, AX calls, device discovery, permission reads, network, documents or preferences.

The final 192 cases cover widths 320/640/844/1280, fonts 11/16/20, Select/Pen/Highlighter/Pointer, selected/no staged scene and independent overlay/legacy styles on the owned native scroll view. They check reported width/full height, native viewport/document geometry, uncompressed native picker intrinsic width, containment of the three native AppKit controls, both scroll ends and wide-row trailing alignment. At 320 points the toolbar reports 320 × 53.5 points and retains 974–1130.5-point documents; at 1280 it reports 1280 × 36.5 and preserves trailing gates. Individual native control rectangles/intrinsic sizes and executable/source hashes are retained in the detailed report bound by the receipt.

This proves geometry and programmatic native scroll reachability with inert owners. SwiftUI draws other controls without separate NSControl views; bounds do not prove glyph/pixel visibility, keyboard scrolling, VoiceOver, focus continuity, contrast or operator flow. It is not a whole-window or all-panel qualification. Issue #90 remains open for its remaining full-window/native accessibility validation.

## Failure-artifact retention follow-up

The runner now retains any generated fixture and executable in a `finally` block before its temporary directory is removed. Compilation/runtime failures and timeouts write a bounded phase/type/child-exit-or-timeout JSON, then rethrow the original exception; child stdout/stderr and all Swift assertions remain unchanged. Use distinct report/artifact paths to keep separate runs.

The old 9cb68c9 toolbar still fails the original width assertion, while its generated source, executable and runtime-failure JSON remain available. A fresh run of the current toolbar still passes all 192 cases. `ANNOTATION_TOOLBAR_RETENTION_2026-10-22.json` binds these new runner/proof artifacts separately; the original receipt and proof files remain unchanged historical evidence. No shipping Swift control or fixture Swift body changed.
