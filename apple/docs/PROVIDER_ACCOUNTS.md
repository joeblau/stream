# Provider accounts and event controls

Reviewed against official documentation on 2026-10-02. Open **Destinations → Provider Accounts and Events**. Stream bundles no OAuth application ID or application secret. Use your own registered application and eligible account; a stored credential is not proof of current API permission or public broadcast acceptance.

| Provider | Authorization and discovery | Native actions | External / unavailable actions |
| --- | --- | --- | --- |
| YouTube | Google **Desktop** OAuth client, system browser, PKCE S256 and random-port IPv4 loopback. Enable YouTube Data API v3 and configure consent/test users/verification. Discovery reads the OAuth-selected channel and paginated upcoming broadcasts. | Create event (title, description, privacy, absolute scheduled start); edit an upcoming event's title/description/start; delete upcoming event; import an existing bound RTMP/RTMPS stream into a **disabled** destination draft; refresh known event status/viewers, open/copy public URL; explicitly complete a live event. | Live enablement, stream creation/binding, privacy edits, thumbnails, early/public start, direct chat. Imported keys/endpoints remain in the destination editor's memory until **Apply Destinations**, then only in stable destination-ID Keychain accounts. An imported destination starts disabled. Project configuration saves provider/channel/event routing IDs only; exported projects and recovery documents contain no access/refresh tokens, client secrets or ingest credentials. Reusable Google/Twitch account tokens use `com.joeblau.Stream.mac.providerAccounts`. macOS Restream uses `com.joeblau.Stream.mac.restream`; its one-time read-and-copy migration preserves `com.joeblau.Stream.restream` for legacy/iOS users. A machine migration flag recorded before copying, plus a Keychain marker when writable, prevents sign-out from resurrecting legacy tokens. If an initial Keychain copy fails, repair the missing values through explicit authorization rather than retrying legacy tokens automatically. This change does not remove the legacy signing access-group entitlement.

**Disconnect Ingest** stops one local publisher. It does not imply a remote event was completed, and local recording continues. **Complete YouTube Event** is a separate explicit provider mutation; other publishers and recording continue. Each destination displays actual local publisher connection acknowledgment, available bitrate and acknowledged elapsed time. Remote readings are separate, timestamped, expire after 60 seconds, and become unknown/unavailable after failure. There is no synthetic viewer zero or downstream LIVE status. Local disconnect/all-stop already uses independent destination supervision; optional timed outro/black and a coordinated remote end-all workflow remain unimplemented.

Every event mutation is sent once. A cancellation or lost reply cannot undo an already accepted remote change; refresh before creating again after an uncertain result. Create returns and retains the actual provider event ID in the current account session immediately after acknowledgment. Upcoming refresh deduplicates stable IDs and never creates, starts or replays events. An acknowledged ID absent from a subsequent upcoming list remains cached with unknown state; use **Verify Selected Event** rather than guessing that it ended or creating a duplicate. The cache is capped at 2,000 event records. Selected routing IDs persist when a destination is applied. Unbound new-event selections are rediscovered by provider refresh after restart; there is no separate persisted pending-event catalog or cross-provider schedule coordinator. Thumbnail upload and partial multi-provider scheduling remain open work.

OAuth token refresh coalesces concurrent requests, saves rotated refresh tokens, and rejects late replies after disconnect/client replacement. Revoked refresh grants require reauthorization. Read-only requests may retry once after 401; mutations never retry automatically. Rate/quota errors produce allowlisted messages and an API cooldown (`Retry-After`, or 60 seconds when unavailable). Permission/eligibility/approval errors offer repair without echoing response bodies. Desktop HTTP rejects redirects and caps API bodies at 2 MiB; OAuth parsers accept at most 64 KiB. Direct YouTube/Twitch chat is deliberately disabled in this connector; account scopes and ingest connection do not fabricate a chat connection.

## Official evidence

- [Google native/desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) documents external-browser authorization, loopback callbacks, PKCE and optional client secret for installed-app token exchange/refresh. A desktop cannot keep a bundled confidential client secret. [Loopback migration](https://developers.google.com/identity/protocols/oauth2/resources/loopback-migration) distinguishes supported desktop clients from deprecated mobile flows.
- [YouTube broadcast list](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/list), [create](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/insert), [update](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/update), [delete](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/delete), [transition](https://developers.google.com/youtube/v3/live/docs/liveBroadcasts/transition), and [live stream fields](https://developers.google.com/youtube/v3/live/docs/liveStreams) define implemented requests and bound ingestion credentials. Update overwrites mutable fields in requested parts; Stream reads/merges writable snippet fields with an ETag and leaves privacy/content details outside the update. Live enablement and quota/permissions can still reject an authenticated request.
- [Twitch OAuth flows](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/) documents public-client device authorization and refresh without a secret; [token validation](https://dev.twitch.tv/docs/authentication/validate-tokens/) requires startup/hourly checks. [API reference](https://dev.twitch.tv/docs/api/reference) defines current user discovery, stream key, channel title and live viewer data. [Schedules](https://dev.twitch.tv/docs/api/schedule/) are a distinct capability.
- [Restream authorization](https://developers.restream.io/authentication/overview), [authorization dialog](https://developers.restream.io/authentication/authorize-dialog), [channels](https://developers.restream.io/channels/channels) and [upcoming events](https://developers.restream.io/events/upcoming-events) define the implemented read APIs/scopes. Its [event create](https://developers.restream.io/events/event-create) and [destination attachment](https://developers.restream.io/events/event-destination-add) are separate operations, with documented platform-specific restrictions; these writes are not exposed by Stream yet.
- [LinkedIn Live Events](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/live-video/) describes product approval/development versus certified Standard tier and separate member/organization scope families. Its page includes older v2 examples (updated 2023); it is evidence of approval requirements, not certification of current endpoint/version availability. No approved application was available for verification.
- Meta's official [Live Video overview](https://developers.facebook.com/docs/live-video-api/overview) and [Live Video feature reference](https://developers.facebook.com/docs/features-reference/live-video-api/) could not be retrieved in this research environment on the review date. Stream therefore does not invent a current permission list, version or approved live integration from third-party mirrors. Verify with your actual Meta app before implementing/claiming Page API access.

## Validation and limits

`ProviderAPITests` exercises production PKCE/form/callback validation, token parsing/refresh retention, pagination/cycle rejection, stable event ID deduplication, unknown state/viewer absence, permission/quota redaction, event create/edit/complete requests and bound-ingest credential boundaries. `apple/scripts/run_provider_accounts_harness.zsh` compiles production vault, loopback receiver and native account session under Swift 6. It drives real loopback callback sockets and HTTP redirect/oversized-response fixtures, a simulated system-browser response, Google/Twitch HTTP fixtures, public device authorization, scope/validation/discovery, refresh coalescing/rotation/revocation, late-response rejection, GET-only retry, actual acknowledged event receipt and workspace shutdown. Keychain and HTTP are injectable fixture boundaries; the harness does not access the operator's real provider credentials. The full native app builds unsigned.

No authorized app IDs/account grants were available for a real provider broadcast test. These results verify local request/lifecycle behavior, not provider approval, real OAuth consent acceptance, ingest acceptance, live chat availability or public event completion. Issues #133/#134/#135/#169 should retain their remaining provider acceptance and workflow criteria.

## Runtime integration

A `StudioRuntime` retains `ProviderAccountSession(restream: chat.restream)`. Inject it with `.environment(\.providerAccounts, runtime.providerAccounts)` beside the other runtime environments. Call `providerAccounts.shutdown()` during runtime switch/close. Optional recovery binding can use `providerAccounts.recoveryEvents(activeIDs:destinations:)` to persist known routing event IDs and a freshly verified ended state. Live/upcoming does not claim reconnection eligibility. Machine credentials survive workspace shutdown; explicit **Forget Authorization** removes them. The environment is optional so destination editors in isolated fixtures remain usable. Root workspace integration owns those three binding points.
