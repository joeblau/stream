# Shared direct public chat

Reviewed against official provider documentation on 2026-10-02. The native account panel and chat sidebar observe the same `StudioDirectChatManager`, bound once with `chat.bindAccounts(providerAccounts)`. Public messages flow into `StudioChatCoordinator.receive(StudioChatAction)`, its bounded queue, existing favorites/filter/reading-position controls, staged Program comment slots, and existing hardware/guest consumers. They do not create another OAuth session or socket per view. Direct connect/read/send/delete actions never start automatically after login, project load, wake or restart.

| Provider | Implemented reader and verified target | Optional explicit actions | Limits |
| --- | --- | --- | --- |
| YouTube | Fresh owned broadcast ID lookup must return the OAuth-selected channel, live lifecycle and `snippet.liveChatId`; REST `liveChat/messages.list` follows its page token and `pollingIntervalMillis`. | Public text post with granted `youtube` or `youtube.force-ssl`; targeted deletion through the owned chat. | Initial history is limited to what the API returns. REST polling consumes quota; preferred streaming/gRPC `streamList` is not implemented. No threaded reply API is exposed. Composer conservatively caps text at 200 characters as an app limit. |
| Twitch | Fresh validated user-token identity; own authorized broadcaster only; public EventSub WebSocket with `user:read:chat`. Connection is acknowledged only after enabled message/delete/clear/clear-user subscriptions are returned. | User-token public post/reply requires `user:write:chat`; targeted deletion requires `moderator:manage:chat_messages`. | Public Device Code Flow requests only optional grants explicitly selected in the account panel. No cloud/app-token bot, other-channel moderation, private whispers, pins, bans or AutoMod controls. User-token sends may reach every participating Shared Chat channel; composer discloses this before confirmation. |
| Restream | Existing public aggregated reader; adapter resets preserve other providers and local curation. | Existing staged comment actions. | No provider write is inferred from relay identity. Restream public replies/moderation are not implemented. |
| Other direct providers | Explicitly unavailable. Ordinary relay publishing remains available. | None. | An ingest credential proves neither chat access nor an approved provider connector. |

Writes require operator confirmation and current connected/granted/owned context. Send requests execute once, honor Twitch `is_sent`, and create no local message echo. A missing/rejected/uncertain response is not treated as delivered. Deletes always supply the selected provider message ID: Twitch never sends a delete without `message_id`, which would clear a channel. Owner/moderator messages are conservatively protected; Twitch messages older than six hours cannot be deleted locally. API permission checks can still reject a grant. Deletion acknowledgments and public moderation events remove known messages, favorites and queued selections, including a staged featured comment. Staged changes reach Program with **Take** unless Direct Live Editing applies them immediately.

YouTube text, Super Chat, Super Sticker, membership, milestone and membership-gift events use documented display text and author roles. Twitch documented emote fragments classify the message as **Emotes**, while preserving its exact public text. No CDN URLs, monetization labels, reaction counts, image emotes, remote HTML, or viewer metrics are guessed. Avatar URLs are bounded HTTPS metadata only; this adapter does not fetch them. Specialized graphical event styling and alert promotion remain separate work.

Real provider message IDs deduplicate by provider/message identity across reconnects and across a Restream relay carrying that same ID. Envelopes without a provider message ID retain separate deliveries. The first received adapter supplies display/routing metadata. Shared Chat copies with different provider IDs cannot be correlated by content. Queues retain at most 1,000 messages with bounded curation and 4,000 identity tombstones; routes also cap at 4,000. A moderation replay within that bounded window cannot resurrect deleted text. Receipts remain in memory, never in project configuration or diagnostics.

Twitch requested migration opens the provider-issued, validated EventSub URL as-is, continues the previous socket until the new welcome, then retires it; transferred subscriptions are not created again. A lost session resubscribes on a fresh session, with at most three exponential retry attempts per manual connection. Welcome and keepalive deadlines cancel stalled sockets. A disconnect cannot replay missed messages and is disclosed as a gap. Authorization replacement/logout/workspace shutdown cancels that provider's work and ignores late HTTP, socket and mutation acknowledgments. A failure or stop in one reader preserves healthy other readers and local curation. Rate-limited YouTube reads stop and share the account's cooldown; they do not poll faster to recover.

## Primary sources

- [YouTube list](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/list) defines the REST query, returned history/order, page token and poll timing; [streamList](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/streamList) is the preferred streaming alternative, not claimed implemented here.
- [YouTube public message resource](https://developers.google.com/youtube/v3/live/docs/liveChatMessages), [insert](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/insert) and [delete](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/delete) define displayed event types/roles, tombstones, public text posting, authorization and owner/moderator deletion.
- [Twitch chat authorization](https://dev.twitch.tv/docs/chat/authenticating/), [EventSub subscription types](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/) and [event payloads](https://dev.twitch.tv/docs/eventsub/eventsub-reference/) distinguish installed user-token scopes and documented public notifications.
- [Twitch WebSocket lifecycle](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/) defines welcome/keepalive/migration and missing replay after unexpected disconnect. [Subscription creation](https://dev.twitch.tv/docs/api/reference/#create-eventsub-subscription), [public send](https://dev.twitch.tv/docs/api/reference/#send-chat-message) and [targeted deletion](https://dev.twitch.tv/docs/api/reference/#delete-chat-messages) define actual API acknowledgments, shared-chat behavior and deletion limits.

## Validation and remaining acceptance

`apple/scripts/run_direct_chat_harness.zsh` compiles the production native manager, socket boundary, public decoders and common queue under Swift 6. Injected HTTP/WebSocket fixtures exercise exact requests, scope gates, poll interval/page tokens, Unicode/roles/event kinds, cross-adapter deduplication, provider send denial/no retry/no synthetic echo, targeted deletion/tombstones, old-socket delivery during migration, no migrated resubscription, fresh resubscription after loss, independent stop, shutdown and noncooperative late responses. Provider OAuth tests verify optional scopes are explicitly selected and unsupported scopes never reach authorization. The existing provider-account and Restream queue harnesses remain required.

No authorized public live feed, approved application grant, or external user message was used for validation. Real Google/Twitch consent and read acceptance, live ordering/rate behavior, provider-side reply/delete acceptance, and actual Program presentation with an authorized feed remain acceptance blockers for #139. Specialized image reactions/emotes, alert styling/promotion and cross-provider viewer presentation remain open #142/#143 work. A fixture pass is local software evidence, not provider acceptance.

## Integration hook

Root runtime owns account/coordinator construction. Add only `chat.bindAccounts(providerAccounts)` after constructing its retained account session; preserve root's newer recording-message/fingerprint properties when merging coordinator changes. Existing `chat.shutdown()` stops both direct readers and Restream. `providerAccounts.shutdown()` stops readers as well, without deleting machine credentials. Views reuse the retained manager in sidebar and account settings. No workspace/app entry point is modified by this isolated change.
